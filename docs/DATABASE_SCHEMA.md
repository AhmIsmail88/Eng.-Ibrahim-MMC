# Database schema — revision 0006 (… + inventory)

Engine: SQLite 3 via SQLAlchemy 2.x, Alembic migrations (`migrations/versions`).
Per-connection PRAGMAs: `foreign_keys=ON`, `busy_timeout=5000`, `journal_mode=WAL`, `synchronous=NORMAL`.
Timestamps: UTC ISO-8601 strings. Booleans: 0/1 with CHECK. No floats for money/quantities.

| Reference | `locations`, `asset_categories`, `asset_types`, `maintenance_task_library`, `failure_codes`, `units`, `currencies` |

Notable constraints: case-insensitive unique `app_users.username` (expression index),
`app_users.role IN ('admin','editor','reports','viewer')` with `password_hash NOT NULL`,
partial unique index on active `notifications.condition_key`, `locations.parent_id <> id`,
`unique(group_code, code)` on failure codes, role/severity/status CHECKs.
Audit log is append-only by convention and by absence of any update/delete API.

## Migration 0002 (accounts)

`0002_user_roles_permissions` only matters for databases created before ADR-025: it
collapses legacy roles (`maintenance_engineer`/`storekeeper` → `editor`) and rebuilds
`app_users` with the new CHECK and a NOT NULL `password_hash` (legacy NULLs get the
`!reset-required` sentinel, which cannot authenticate). Fresh databases already have the
target shape from `0001`, so the migration exits immediately.

## Migration 0003 (assets & meters)

Adds the Phase 1 operational tables. Two notes for implementers:

- `uq_assets_code_ci` is an **expression index** (`lower(trim(asset_code))`). Alembic
autogenerate cannot reflect expression indexes on SQLite, so it is created by hand in
the migration; a future `--autogenerate` will not see it and must not drop it.
- `operating_calendar_shifts` stores real shift windows (`start_time_local`,
`end_time_local`, `ends_next_day`) rather than "hours per day", so a 22:00–06:00 shift
and multiple shifts per day are representable (SPEC 16.3). `operating_calendar_revisions`
is deferred to Phase 5 with the Availability report.

## Migration 0004 (failures & work orders)

Adds the maintenance tables. Notes:

- `work_orders.wo_number` and `failure_reports.failure_no` are plain unique columns;
they are generated by `code_sequences` inside the inserting transaction (`WO-YYYY-NNNNNN`,
`BR-YYYY-NNNNNN`), never by `MAX()+1` (SPEC 10.8).
- The status domain is duplicated deliberately as a DB CHECK and as the state machine in
`domain/policies/wo_state_machine.py`; the transition rules live only in the policy (ADR-007).
- `work_order_time_logs` carries `hourly_rate_minor_snapshot` + `currency`, so a rate change
later does not rewrite history; a pre-check prevents overlapping logs per technician.
- `downtime_events.ended_at` may be NULL (open event); at most one open event per asset is
enforced in `DowntimeService`, not by a partial index (analytics still unions intervals).

## Migration 0005 (preventive maintenance)

- `pm_occurrences` has `UNIQUE(plan_id, due_key)` — the database, not a UI guard, is what
makes “one work order per occurrence” true (SPEC 9.4). `due_key` is derived from the due
anchor (date or meter), so regenerating the same occurrence cannot create a second order.
- `pm_plans.next_due_meter` / `meter_interval_value` are stored as exact decimal text,
consistent with meter readings; `next_due_date` is a local date (no UTC conversion).
- Inspection tables are created in the same migration but their service/UI ships in Phase 3b;
`inspection_answers` snapshots the item definition (`item_snapshot_json`) so template edits
never rewrite a completed inspection.

## Migration 0006 (spare parts & stock ledger)

- `stock_movements` is the only writable stock journal. Every row is immutable: corrections
are new `reversal_of_id` movements, returns are `RETURN_FROM_WO` linked by
`original_movement_id` (ADR-016).
- `stock_balances` is a cache that is updated in the same transaction as the movement;
`available = on_hand − reserved` and negative on-hand is rejected before writing.
- `work_order_part_usage` is a **VIEW**, not a table: net quantity/value are derived from
issues and returns, so no second source of truth exists.
- `uq_parts_code_ci` is an expression index created by hand (same SQLite/autogenerate caveat
as `uq_assets_code_ci`).
